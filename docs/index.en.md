title: The MCP server
description: The machines handed to an agent over the Model Context Protocol — stood up by name or from a snapshot, run, stepped, stopped, watched, captured where they match and counted, into the answer or into a file, called into, read and written, seen, read back as instructions, typed at, given discs and tapes, saved, kept as they stand and put back there, and journaled.

An agent has no eyes on the glass and no fingers on the keys, and what it learns of a machine is what it asks for. This server is where it asks. It speaks the [Model Context Protocol](https://modelcontextprotocol.io) over its standard input and output, to one client at a time, and holds as many machines as that client stands up, each behind a handle of its own.

## Starting it

`make` builds `target/release/colophon-mcp`, and the server is started with the directory its firmware is read from:

```sh
colophon-mcp --roms ../colophon-emulator/roms
```

The directory holds the firmware as the emulator's `make roms` fetches it: `cpc6128.rom`, `cpc664.rom` and `cpc464.rom`, each the operating system followed by BASIC; `amsdos.rom`, for the machines with a disc interface; and `spectrum48.rom`. A file is read when a machine that needs it is opened, so a missing one is reported then, by name, and nothing else is refused for it. A file must be the size of the firmware it is named for, where the emulator's command line takes the first bytes of a longer one.

A client is given the same command line, which it starts and speaks to. With Claude Code:

```sh
claude mcp add colophon -- /path/to/colophon-mcp/target/release/colophon-mcp --roms /path/to/colophon-emulator/roms
```

## What it answers

A request that names its revision in its `_meta`, as the 2026-07-28 revision has every request do, is answered in the revision it names, `server/discover` among them. A client that opens with `initialize` instead is answered in 2025-11-25 or 2025-06-18, as it asks, and in 2025-11-25 if it asks for any other. A request in a revision the server does not speak is refused with the ones it does.

`machine_open` builds a machine by the name the emulator's command line gives it, and wires it as the command line does: the same RAM, the same firmware in the same sockets, and the disc interface where the machine has one. Given a snapshot, it loads it as the command line does, into the machine named, once the firmware is fitted. `machine_list` names the machines standing, and `machine_close` puts one away once what it was asked before is done. `run` and `step` move a machine, and `call` runs a routine of its own; `inspect` and `set` read and write what it holds, and `peek` and `poke` its memory. `monitor` shows its picture, `screen` reads a CPC's memory as one, and `disassemble` reads its memory as instructions. `type` types at it and `run` holds its keys down, `disc_insert` and `tape_insert` give it a disc or a tape, and `snapshot_save` writes it to a file. `state_keep` keeps it as it stands, `state_restore` puts it back there and `state_drop` lets a state go, and `journal` lists what has been done to it. Each tool's description is the reference for it; an agent reads them from the server.

An address or a port is answered in hexadecimal after `&`, `&BB06`, and so is a byte a run gathers, `&3E`, as a CPC's own manuals write them and as `disassemble` writes the numbers in its instructions; an address past `&FFFF`, in a 6128's second 64K, takes five digits. A register of a CPC's sound chip, its PSG, is a number, `7`, as SOFT 968, Amstrad's firmware manual, numbers them. The bytes `peek` and `disassemble` answer are pairs of digits, as `poke` takes them. A request may give an address in the forms its schema lists, and the journal writes every address and port a request gave after `&`, whatever form it came in, and a range of one address as that address, or of one register as that register; the values `set` and `call` write it keeps as they were given. `inspect` and `set` answer the emulator's struct as it holds it, in numbers, and `set` takes hexadecimal for a field of unsigned integers too. An argument of the wrong kind is refused with its name, and no schema names a format, since every format JSON Schema defines is of strings and a client need not know any other.

## Time

Nothing but `run`, `step`, `call` and `type` moves a machine, and each answers with the ticks it took, the frames the monitor retraced in them, and the machine's tick since it was stood up: from power-on, or from its snapshot. `state_restore` puts a machine back at a tick it stood at before. The same requests of the same machine give the same answers.

A run goes by frames or by ticks. A frame is the monitor's and ends as its retrace sends the beam to the top-left corner, so a run by frames leaves a whole picture on the monitor; a CPC's frame is whatever its 6845 is programmed to make and may never come, so such a run is held to twice a standard frame's ticks for each frame asked. A run by ticks runs that many, which is how the emulator's command line counts its frames: 79872 ticks to a CPC's, 69888 to a Spectrum's. A step runs instructions, each to its end and through the response to an interrupt taken there, so a step can land in a handler. A run or a step ends between instructions, a few ticks past what was asked if the instruction standing there runs on, unless it ends inside a chain of prefixes, which is no instruction until it is done; the answer then says it stopped unsettled. A run stops sooner at the end of a `HALT` that leaves interrupts disabled, and says it stopped halted: the processor waits there for good, since IFF1 shuts out the interrupt and neither machine raises the non-maskable one, so nothing the machine does of itself carries it further. A run that begins there runs as asked, so the frames a whole picture wants still pass, unless `set` has written in a non-maskable interrupt, which wakes it. Typing takes its ticks all the same.

One request runs at most 1500 frames, or the ticks of 1500 standard frames, which is half a minute of either machine's time, or a minute of a CPC's whose frames do not come; or 100000 instructions, under a second. On the machine the server was written on, 1500 of a CPC's frames run in about six seconds, well inside the minute a client of the protocol's TypeScript SDK waits for an answer.

## Stopping and watching

A run can be told where to stop and what to watch for on the way, and a condition says either in the same words: an instruction about to begin at an address or in a range, a byte read or written there, a port read or written, or a register of a CPC's PSG written. A port is matched on the address lines its device decodes, which the condition names, because a CPC's chips each answer a few lines of the address and not one number. An instruction or a read may also be asked to come from the RAM, or from a ROM: a CPC's Gate Array enables its lower ROM, the firmware, over `&0000` to `&3FFF`, and an upper ROM, chosen by its number, over `&C000` to `&FFFF`, and [while a ROM is enabled the processor reads it, and its writes go to the RAM beneath](https://web.archive.org/web/20260710174425/https://www.grimware.org/doku.php/documentations/devices/gatearray), so that `&0038` is the firmware's while the lower ROM is enabled and the RAM's while it is not. A Spectrum's ROM is below `&4000` for good. A CPC's processor reaches its PSG, the AY-3-8912 that is its sound chip, through the PPI: [port A carries the PSG's data and the top two bits of port C its function](https://web.archive.org/web/20220626135348/https://cpctech.cpcwiki.de/docs/psg.html), and while those bits give WRITE the PSG takes port A's byte into the register it has selected. The emulator runs the PSG at each access to the PPI, by port C as the access leaves it, so each access that leaves port C giving WRITE is a write and a match: an `IN` from the PPI and the PPI's bit set/reset among them, often the same byte to the same register again. A `psg` condition names registers by their numbers, 0 to 15, and its matches give the byte port A gave the PSG, of which a register narrower than eight bits keeps only its low bits. The tests write registers through the routine [cpctech](https://web.archive.org/web/20220626135348/https://cpctech.cpcwiki.de/docs/psg.html) gives for it and through the firmware's MC SOUND REGISTER and SOUND QUEUE, and find the writes where [a listing of the 6128's firmware](https://github.com/Bread80/CPC6128-Firmware-Source) makes them, in its order. A run given conditions in `until` stops at the first match: before the instruction, so that the machine stands at it unrun, or at the end of the instruction that made the access, so that it stands between instructions as every run leaves it. A run that begins on an instruction it was stopped before runs that instruction first. Conditions in `gather` are listed rather than stopped at, each match with the tick it came at, the address, the port or the register and the byte, where the instruction that made it begins, and where the monitor's beam then stood; a port read gives the byte the processor took, which a CPC's board can change while it holds the read. On a CPC a match also says which memory held its instruction or its byte, where the address alone does not: `rom` names the lower ROM, or an upper ROM by its number, as [WinAPE's debugger](https://web.archive.org/web/20160525234943/http://www.winape.net/help/breakpoints.html) names an upper ROM's block, and `ram` the RAM's own address, where a 6128's RAM configuration pages it in elsewhere, as `peek`'s `ram` counts it; `pc_rom` and `pc_ram` say the same of the instruction that made an access. A number selected with no ROM fitted is answered by ROM 0, as [Kevin Thacker's cpctech](https://web.archive.org/web/20190604090025/http://cpctech.cpc-live.com/docs/exprom.html) says BASIC is, and the tests find the 6128's firmware walking its ROMs as [its listing](https://github.com/Bread80/CPC6128-Firmware-Source) walks them, from ROM 15 down to 1, reading ROM 0 at each number but 7, where AMSDOS answers, and starting BASIC and then AMSDOS at `&C006` of each; they find the firmware's interrupt entry at `&0038` run from the lower ROM and from the copy the firmware makes of it in RAM, and a condition on the RAM's stopping only at the copy. A list fills at 128 matches, keeps the rest of the instruction that made the 128th and of the response to an interrupt taken at its end, and stops the run where every run stops, so that the next run gathers on from there and nothing is lost between them. The matches a run gathers are those a run stopped at each of them in turn would stop at, and the tests hold the two to each other. Given `gather_last`, a run keeps the last 128 matches instead, and runs on past them as though nothing filled, so that one stopped by `until`, or at its end, lists what led there; the tests hold it to the tail of a gathering carried through many runs, and find the last instructions of a routine in the 48K ROM where its disassembly ends it.

A condition in `until` or `gather` may also capture the machine at each of its matches, so that what would be read after a stop comes with the match: values of the processor, each by the path `inspect` reads it at under `cpu`, and spans of memory, each read as `peek` reads it. An instruction about to begin captures the machine it finds, as a stop before it leaves the machine. An access captures the machine as the instruction that made it leaves it at its end, where a stop on the access stands, and every access of one instruction alike, so that both writes of a `PUSH` capture the stack pointer it leaves; inside an instruction the processor's registers stand in the emulator's own order of working, which no documentation grades. An interrupt taken at the end of the instruction is accepted before the capture and answered after it, and the stop runs on through the response, so there the two differ: the capture has the instruction's program counter and stack, but IFF1 clear, as [the processor clears it as it takes the interrupt](https://www.zilog.com/docs/z80/um0080.pdf), and IFF2 with it if the interrupt is INT, and the emulator's own machinery for the processor standing as the response begins. An access the response itself makes captures the machine at the response's end. A match answers what it captured in its `captured`, and a match of several conditions captures what each of them names. A gathering any of whose conditions captures fills at 32 matches, or with `gather_last` keeps the last 32, since each carries more; with a `path` it fills at 1048576 as any gathering does, each line with its capture. The tests hold every capture across a stretch to what a stop at each of its matches reads back with `inspect` and `peek`, and to what a twin gathering over the same stretch captures; they find the capture before the response to INT and to an NMI written in with `set`, and TXT OUTPUT, at the address [the 6128's firmware listing](https://github.com/Bread80/CPC6128-Firmware-Source) gives, handed each character BASIC's `PRINT` prints, one call at a time, in A.

Conditions in `count` are counted rather than listed: each place that matches, an instruction begun at an address, a byte read or written there, a port by the whole of its address, or a register of the PSG, is answered once, with how many times it matched, executes first, then reads, writes, ports and the PSG's registers, each kind by address or register, or by pc. A place in memory is a byte of it, so that on a CPC the lower ROM's `&0038` and the RAM's are two places, as are a 6128's two banks of RAM at one address, and a byte the processor reaches at two addresses, as a 6128's RAM configurations can page one, is one place, told by the address of its first match. Each is told by its first match, with its tick and where the instruction that made it begins, and an instruction with the bytes the processor fetched as it first began there, so that code a program writes, runs and wipes again still says what ran. A count asked to run over `&4000` to `&BFFF` says which of a program's instructions ran, how often and when each first did, and one over a single address how many times the instruction there began. A count by `pc` counts an access by where the instruction that made it begins rather than by its address, so that a count of the writes to a screen says which instructions wrote it and how many writes each made; the response to an interrupt is no instruction, so what it does, the return address it pushes and the vector it reads in mode 2, is then not counted. The tests count the 48K ROM clearing its screen so, and find the four instructions its disassembly names, each first writing where the disassembly says. Counted by address, a port is the whole address on the bus, whatever bits the condition's mask decodes, so a port whose address carries the value written, as `OUT (n),A` puts A on the high byte, is counted at as many places as there are values. It fills at 256 places, keeps the rest of the instruction that filled it, and stops the run where a full gathering does; the next run counts afresh from there. A count is a gathering tallied by place, by address or by `pc`, and each place is told by the first match gathered there since the run began; the tests hold the two to each other.

An answer is bounded to what a model can take in, and a question about every frame of a stretch is bigger than that. Given a `path`, a run or a call writes what `gather` and `count` find to a new file instead, a line of JSON for each match and each place, as the answer would list it, after the list it belongs to, the matches first, for a client to read with tools of its own. The answer names the file by its path and its SHA-256 and says how many lines each list holds. Written so, a count never fills, so a run by frames counts all its frames, a map of every byte a program reads and writes over them; and a gathering fills at 1048576 matches, some 100MB, or some 750MB where each captures all a request may name, where an answer's fills at 128, which holds a trace of every instruction a program runs over a hundred frames or so, and its writes to the PSG over many more. The file is made before the run begins, only where no file is, and a request whose file cannot be made is refused with the machine as it stood. It stands empty at its path through the run, and is written once the run is over, before the answer, so a file holds what it is to hold once an answer names it by its hash. One that cannot be written whole then is taken away again, and the request, which is not taken back, is refused with how far it ran and where the machine stands, and journaled without the file. The tests hold a file to what runs that fill and go on list over the same stretch, and to what a twin's answer lists.

A read is the program reading memory as data. The bytes of an instruction are never one: its opcodes are told by the processor's M1, and its operands by the emulator, which knows them where the bus does not. The return address an interrupt's response pushes names no instruction, because none made it.

`call` runs a routine the machine holds as its own `CALL` would: the program counter is pushed where the stack pointer stands, and the call ends when the processor comes back to it with the stack pointer where it was, which is where the routine's own return leaves it. A machine called into thus stands where it stood, with whatever the routine left in its registers and memory, and a processor halted on `HALT` is halted again once the routine has returned within the call. The values given with a call are written first, as `set` writes them. A routine that halts on `HALT` with interrupts disabled stops the call there, as it stops a run, and the call says so at once rather than waiting out its frames: a routine that waits on `HALT` for the next frame, called with IFF1 clear, as inside an interrupt's handler or after `DI`, waits for good. A call is refused, and the machine left as it was, where the address pushed would not read back, under a CPC's enabled ROMs or in a Spectrum's, and inside a chain of prefixes, which is no place between instructions. Interrupts stay as they stand, so their handlers run within a call only if IFF1 is set: a run by frames ends just past the retrace, which on either machine's firmware comes inside the handler of the frame's interrupt, with IFF1 clear, and a routine called there runs with no interrupt at all unless it enables them itself, as the tests find on both.

## What a machine holds

`inspect` reads the emulator's own struct for the machine, `cpc_t` or `spectrum_t`, by the path a C expression gives a field of it: `cpu.pc`, `crtc.registers[12]`, `fdc.units[0].head`. Its fields keep their headers' names, and a C enum's value is its enumerator's name; pointers are not followed, and `peek` reads memory instead. Some fields are the chips' registers and counters; others are the emulator's machinery for stepping them a tick at a time, which no silicon holds as such, and the headers say which.

`set` writes by the same paths, every value given or none. The core indexes and sizes by some of its fields without checking them, because nothing it does takes them out of range: the size of the RAM, the RAM configuration of a 64K machine, the pen that picks one of the Gate Array's seventeen inks, the PSG's selected register, the disc controller's counts of the bytes it has taken and given and the drive its command chose, the monitor's size, and the processor's count of the cycles under way. A value past those is refused, with the range that would do, and so is a WAIT written on a Spectrum's bus, which nothing there drives and which would hold its processor for good; the machine stands as it was. A CPC's memory map is worked out again after every write, and a Spectrum's ULA stood at the tick of the frame its `frame_tick` names, from which its beam is reckoned.

`peek` and `poke` reach memory as the processor would: through a CPC's banking and its ROMs, so that a write under a ROM lands in the RAM beneath it, and into a Spectrum's ROM not at all. `peek` also reads a CPC's RAM itself, by the RAM's own addresses as a base given to `screen` counts them, whatever is paged in: the RAM beneath the ROMs, and a 6128's second 64K at `&10000` to `&1FFFF`.

## The picture

`monitor` answers with the picture on the machine's monitor as a PNG, beside the JSON that says which machine, at which tick, how large, and where the monitor's beam stands. The picture is cut and drawn as the emulator's command line cuts and draws its screenshots, so that one written there and one shown here can be laid over each other and compared pixel for pixel, which the tests do: a CPC's 768 by 544, a sample of the raster to each pixel across and each line drawn twice, and a Spectrum's 352 by 264. Each pixel's index in the PNG's palette is what the machine put on the cable, a CPC's hardware colour code or a Spectrum's four bits of brightness and colour, and the palette is the colour each stands for, so an agent that reads the file gets the machine's numbers back. The beam paints the picture as the machine runs, so after a run by frames that ran all its frames it is whole, and after any other run, a step, a call or typing the lines above the beam are this frame's and those below it the frame's before; the answer's `whole` says whether the beam is partway through the picture. A line that a frame shorter than the picture never reaches keeps what an earlier pass left there.

`screen` reads a CPC's memory as a picture, as [the player's screen panel](https://github.com/tulinmola/colophon-player/blob/main/docs/debugger/screen.en.md) reads it and with the same names for what it is given: `video`, the way the CPC's video hardware reads the screen; `linear`, a flat buffer; or `columns`, one that runs down before across, so that a sprite sheet, a font or a buffer built off the screen shows its shape when read in the layout it was written in. Whatever is not given is read from the machine as it stands: the start, the width and the height from the 6845, and the mode in force and the sixteen inks from the Gate Array, so that a screen asked for nothing draws the memory the 6845 is displaying, at the scale `monitor` draws it, and the tests hold the two to each other in each of the four modes, and with the 6845 counting rows of five lines and of sixteen, starting partway into a 2K, and carrying a screen of 32K from one 16K into the next. It reads the RAM as the video hardware does, whatever ROM the processor sees over it: the `video` reading the base 64K, and the others a 6128's second 64K as well, at `&10000` to `&1FFFF`. Each pixel's index is its pen rather than a colour, so the pen a sprite's mask keeps clear stays one number in the file whatever ink it is given.

## Reading memory as instructions

`disassemble` reads memory as the instructions the processor would run from an address on, each with its address, its bytes and what they say, through the banking and the ROMs as `peek` reads it. It writes Zilog's mnemonics, numbers in hexadecimal after `&`, and the target of a relative jump worked out, and names the undocumented instructions as [the player's disassembly](https://github.com/tulinmola/colophon-player/blob/main/docs/debugger/disassembly.en.md) names them, `ED FF` among them as WinAPE's `BRK`. An instruction is what `step` runs, so a chain of `DD` and `FD` prefixes is one instruction, ruled by its last prefix. `make test-disassembly` holds every instruction of the 48K ROM to [The Complete Spectrum ROM Disassembly](https://skoolkid.github.io/rom/), and every opcode to SkoolKit's own disassembler, save where the player's names differ from SkoolKit's, and where SkoolKit leaves a `DD` or `FD` that changes nothing as a byte of its own, which the listing joins to the instruction after it as the processor does.

## Keys and typing

A machine is reached through its keyboard as a person reached it, a key at a time, and what a key means is its firmware's business. `run` takes keys to hold down from its start to its end, on top of whatever the keyboard holds already, and leaves the keyboard holding what it held before; a stretch of a game played with a direction and fire held is a run with those keys, and the next stretch another run. A key goes by the name [the player](https://github.com/tulinmola/colophon-player) prints on it, after the keys SOFT 968, Amstrad's firmware manual, draws for a CPC, `SPACE`, `COPY`, `f5`, and `(FIRE 2)` for joystick 0's main button, and after the legends on a Spectrum's, `CAPS` and `SYM` among them. A CPC's key may also be given by the number its firmware gives it, its line of the matrix times eight and its bit, which is the number a game's own code tests.

`type` types text as the emulator's command line types it with `--type`: each character's key held down, with whatever shift it needs, for 3 standard frames, then let go for 3 on a CPC and 6 on a Spectrum. Those are the command line's counts, measured there: a CPC's firmware marks a key let go only once two of its scans have missed it, and a Spectrum's takes the same key again only once five of its scans have passed. A newline is RETURN or ENTER, and on a CPC a tab, an escape and a backspace are TAB, ESC and DEL. A text is ASCII, at most 250 characters on a CPC and 166 on a Spectrum, 1500 frames' worth, and one holding a character no key types, alone or with a shift, is refused before a key goes down; a key that types no character, or a character outside ASCII such as a CPC's £, is held through `run`. Keys the keyboard holds already, as `set` writes them, stay held through the typing, where the command line lets every key go. The keys go down and come up between instructions, a few ticks at most from where the command line puts them, counting from where the typing began, and the typing ends at the end of the instruction standing when its frames' ticks have run out, or where a stretch of it ends inside a chain of prefixes, as a run does. The tests type `PRINT 2+2` at each CPC and `p2+2` at the Spectrum, after the frames the command line waits, and the screen's memory is what the command line's typing leaves there; the firmware's answer, read in its own font, is 4. They hold keys through a run and BASIC's INKEY reads them as the CPC 6128's manual says it does, and a Spectrum held at CAPS and SPACE breaks into its program with report L.

A Spectrum's ROM reads a letter typed where the cursor shows K as a keyword, so `p` at the start of a line is PRINT and `j` is LOAD. Neither firmware takes a key before it has started: the command line waits 78 frames on a CPC, and 128 on a Spectrum, whose ROM takes none before frame 85.

## Discs and tapes

A disc or a tape is given as a file, which is read whole and copied into the machine, and named in the answer by its SHA-256, with the tick at which it went in. Nothing the machine does reaches the file.

`disc_insert` puts a DSK image, of the original layout or the extended one, in a CPC's drive A or B, with room past it for every track to be formatted again, as the command line gives one with `--disc`. What the machine writes lands in its copy, and is gone once another disc takes the copy's place, as a game's second side does when the game asks for it, save what a state kept while it stood in the drive brings back as it stood then. A cpc664 and a cpc6128 take discs. A cpc464 does not: it is built here as the command line builds one given no disc, without the disc interface, and nothing here fits one afterwards. The tests save a one-line program to a blank disc they write in SOFT 968's DATA format, and AMSDOS catalogues it as the CPC 6128's manual shows it does, `EXAMPLE.BAS 1K` and `177K free`; the same file, put in again, is still blank.

`tape_insert` puts a `.tap` or a `.tzx` in a Spectrum's deck and presses PLAY. A Spectrum has no motor line, so the tape plays from that tick on, whatever the machine does, and a header's pilot tone lasts 5 seconds: a tape goes in just before the program asks for it, as `LOAD ""` does. The tests write a tape of one BASIC program as the 48K reference describes what SAVE puts on tape, and `LOAD ""` reads it and runs it from its autostart line.

## Saving a machine

`snapshot_save` writes a machine to a file in the format the command line writes with `--save` and `machine_open` reads: an SNA of version 1 for a CPC, the 48K `.sna` for a Spectrum. It writes only where no file is, so that nothing is ever written over, and the answer names the file by its SHA-256, with the machine's tick. A snapshot keeps less than the machine, as the last section says. It keeps the machine's RAM whole, so the file is an image of it for tools of the client's own: a CPC's all of it after a header of 256 bytes, by the RAM's own addresses, and a Spectrum's after a header of 27, from `&4000`, save the two bytes below the stack pointer, which carry the program counter. The tests hold a snapshot the server saves to the one the command line saves of the same machine, byte for byte, and one the command line runs on from to where the server, opening it, runs on to.

## Keeping a machine

A machine can be kept as it stands and put back there, as often as an agent wants to try one thing and then another from the same place. `state_keep` keeps everything the machine holds: its processor inside an instruction if a run left it in a chain of prefixes, where no snapshot has room for it, its picture, each disc as it has been written, the tape where it has played to, its tick and its journal. `state_restore` puts the machine back exactly so, its discs among it though another disc has taken a drive since, and a run from there goes on as it went on from the moment kept. The tests hold a CPC kept while AMSDOS writes its disc, its disc controller inside a command, and a Spectrum kept partway through `LOAD ""` to the machines they ran on to, and a stretch gathered again from a state to the stretch gathered live. Restoring a state drops no other: each is a branch to come back to. `state_drop` lets one go, and `machine_list` names those held of each machine.

A state is held in the server's memory, beside its machine, and is restored into that machine alone, because it holds the machine's own pointers, a CPC's into itself, and at its buffers. For the same reason it is never written to a file, and it goes with its machine, or with the server. States kept while a disc does not change share one copy of it.

## The journal

A finding is to leave as something the machine can be asked again, and `journal` is that: the build that runs a machine, the files it was built from, each by its SHA-256, and every request that stood it up or changed it, in order, the first of them the `machine_open` that stood it up, each with the machine's tick as it began and the arguments it was given, save that an address or a port is written after `&`, a register of the PSG as a number, a range of one address or register as that one, and a path absolute, and a snapshot, a disc or a tape read named by its SHA-256 as well, and a file a run or a call wrote named by what it holds. Reads are not entered, nor are states kept or let go; a restore makes the journal the state's, so the journal is always the way from the machine's opening to where it stands. The same requests made in the same order, on the same build and with the same files, make a machine that stands as the first stands, which the tests do, with a branch a restore left behind; a request that wrote a file writes one that holds the same, at a path that names nothing yet. A long journal is answered a page at a time.

## The files a machine is built from

`machine_open` answers with every file the machine was built from, its firmware and its snapshot, each by its path and the SHA-256 of what it held, and `disc_insert` and `tape_insert` name their files the same way. A finding names its copy by that hash, and a file changed between two openings gives two hashes. A path is read and written on the file system the server runs on, from its working directory if it is relative, and the answers and the journal name the file by its absolute path, so that a journal is made again from anywhere; a file that cannot be reached is refused with that path and the working directory. Anything there but a file is refused unread, firmware, snapshot, disc or tape, and so is a snapshot longer than 49179 bytes for a Spectrum, the one length its snapshot has, or than 8MB for a CPC, whose version 3 may carry chunks after its memory, and a disc or a tape longer than 16MB.

## The name of the build

The server names itself and the build in the `_meta` of its answers to `server/discover`, `tools/list` and `tools/call`, as the 2026-07-28 revision asks of every result and the older ones allow, and in the `serverInfo` of its answer to `initialize`. A ping's answer does not, nor an error, nor the empty answers the protocol's library gives for what the server does not offer. The name is the package's own version, then the commit of this repository and the commit of the emulator it was compiled from.

```
0.0.0+mcp.<commit>.dirty.emulator.<commit>
```

`.dirty` follows a commit whose files differ from the build's, an untracked file among them, or an ignored file of a kind the build compiles: here, the sources, the bridge, the build script and the files that pin the crates and the toolchain; in the emulator, its `src/`. A change anywhere else in either repository does not mark the build, because nothing compiled from it changed. Where a repository is not a checkout of its own, the commit is `none`. A finding can be made again only on a build that is unmarked and names commits the published repositories hold; one made on any other build is made again on such a build before it leaves.

## What it cannot do

- `type` keeps the command line's pace, and a program that reads the keyboard only now and then, or throws keys away while it is busy, loses those pressed between. It is typed at a character at a time, with runs between that stop where it reads the keyboard.
- Keys are held down for the whole of a run. Nothing presses or lets go of one partway through, so a stretch that wants a key for part of it is two runs, and `step` and `call` take no keys; `set` can write the keyboard's lines, which then stay as written.
- A cpc464 takes no disc, so a release for one is read here on a cpc664 or a cpc6128, or from a snapshot.
- A disc comes out of a drive only as another goes in, or as a state kept while the drive was empty is restored. No disc is written out, so what a program saves to one lives in the machine and in the states kept since, and leaves with no file.
- A CPC takes no tape. The emulator plays one to a CPC's play head, but has never loaded one through its firmware, so nothing here could hold such a loading to what the machine did.
- A tape that stops itself, as a multiload's does between its parts, waits there: nothing presses PLAY again, though a state kept before it stopped puts it back playing where it was, and no tape is stopped or taken out but by another put in, or by a state kept before it went in.
- A snapshot carries less than the machine. Neither format keeps whether the processor is halted, so a machine saved on HALT, waiting for an interrupt, runs on past the HALT as soon as it is read. A CPC's is read and written for the fields of version 1 alone: the 6845's counters a version 3 carries are not read, so the machine begins its frame again from the top, with the Gate Array's interrupt counter and the monitor's beam at 0, and its first run by frames ends early, at the retrace the 6845's first vertical sync brings; no version keeps the disc controller or the discs, so a machine read from one finds the controller as at power-on: one taken inside a disc access does not go on with it, and AMSDOS, which sets the controller up with SPECIFY as the machine starts, reads no disc from there, as the tests find with a catalogue that fails, until `set` writes `fdc.non_dma` back as SPECIFY left it. A Spectrum's has no room for the beam or the tape, so one taken while it loads comes back to an empty deck, and keeps the program counter in the two bytes below the stack pointer, so a machine read from it has lost what those two bytes held; a Spectrum whose stack pointer is below &4002 is not saved, 0 among them, though a stack pointer of 0 pushes to the top of the RAM. Nothing a version 3 carries in chunks after its memory dump is read, so one that keeps its memory in chunks rather than in the dump is refused.
- A file is written only where none is, and the only files written are a snapshot and what a run or a call gathers and counts; no tool writes memory alone, and a snapshot holds the RAM whole.
- Nothing here reads a run's file back. A client reads it with tools of its own, so an agent given this server's tools and no others has only the answer's lists, 128 matches, or 32 where a condition of `gather` captures, and 256 places at a time.
- A condition lasts one request. No condition is kept on a machine between requests, so a stop wanted again is asked for again.
- A condition names a place, and for an instruction or a read the RAM or a ROM, and nothing more. It cannot ask for a value written, a register's contents or a position of the beam, nor for one ROM rather than another or one of a 6128's banks of RAM rather than another; those are read from what a gathering lists and captures, or by stopping and reading.
- A capture reads what its condition names and nothing more. The processor's values are read one at a time as the emulator holds them, so HL is `cpu.h` and `cpu.l`, and IX `cpu.ixh` and `cpu.ixl`. A span is read at a fixed address, so the bytes at an address a register holds, the return address on the stack among them, are read by stopping and reading. Nothing outside the processor and memory is captured, the 6845's registers and the Gate Array's among them, and a request's captures name at most 16 values and spans, reading at most 64 bytes. A count captures nothing; what the machine held at a place's first match is captured by gathering it.
- `set` can write the processor's machinery into states the emulator never reaches of itself, such as an INT accepted at an opcode fetch, and a run from one does what the core does with it, but what a condition sees there is not promised: the instruction run there is seen to begin by no condition, its accesses name no instruction, and they may capture nothing.
- A ROM that is not paged in is read by no tool: `peek` and `disassemble` reach a ROM only as the processor does, and `screen` reads the RAM alone. Its file, which `machine_open` names by its hash, holds it.
- A count says how often each place matched and when it first did, and nothing of when it matched again, in what order it matched after or for how long. The time a routine takes is read from the ticks of a run that stops at its start and its end.
- An instruction counted keeps the bytes it first ran with. One rewritten and run again at the same address is the same place, so what it held the second time is read by stopping there and reading memory.
- A gathering of the last matches does not say how many it let go; a count of the same conditions in the same run says how many there were, unless it fills and stops the run.
- A variable a program keeps inside one of its own instructions is no data, so a read of it is never matched; the instruction holding it is found by `execute`, and what changes it by `write`.
- No sound is heard. The emulator keeps a CPC's PSG registers and sounds none of them, so what a program plays is read from the writes a `psg` condition gathers; a Spectrum's speaker is [bit 4 of its ULA's port](https://worldofspectrum.org/faq/reference/48kreference.htm), whose writes `{"out": "&FE", "mask": "&01"}` gathers.
- How many writes a `psg` condition sees is the emulator's count. On the board the PSG is [wired to the PPI's ports A and C](https://web.archive.org/web/20220626135348/https://cpctech.cpcwiki.de/docs/psg.html) and not to the processor's bus, so it takes port A while port C gives it WRITE and sees no access to the PPI; the emulator writes at each access, so a program that leaves WRITE standing while it reads the PPI's other ports is matched writing the same byte again at every read.
- Only writes to the PSG are conditions. A register selected, or read, as a CPC's firmware reads its keyboard through register 14, is found by watching the PPI's ports with `in` and `out`.
- A state is kept only when asked. Nothing keeps one as a machine runs, so a stretch is asked about again from a state kept before it, restored and run again with what is to be gathered, or from a machine made again by the journal's requests.
- States live in the server's memory, 64 of a machine at most, each restored into the machine it was kept from alone, and none is written to a file, so none outlasts the server. Neither does the journal: what outlasts the server is what a client read of it, and the files it names, from which the machine is made again on the same build.
- Nothing here plays a journal back: a client makes its requests again itself. A journal names a disc or a tape by its path and its hash, so making the machine again wants the file of that hash at that path.
- `call` waits for its own return and nothing else. A routine that leaves another way, by jumping out or by unwinding the stack beneath it, is left running, and so is one that has not returned when the call stops, at its frames, at a condition of `until` or with its gathering or its count full. A later run carries it on and past its return, stopping there only if `until` asks for the address the call was made from, and a processor woken from `HALT` for it is not halted again. One that halts with interrupts disabled waits there for good: `set` or a state restored takes the processor past the `HALT`, and another call wakes it for that call's routine alone.
- A program that ends on `HALT` with interrupts disabled ends its first run there, short of the frames asked, so a picture of where it ended takes a second run.
- `call` pushes and jumps from outside the processor, in no time at all, and leaves its refresh register R and its hidden WZ and Q as they stood, where a `CALL` would have moved them; only a routine that reads them can tell.
- `monitor` shows the command line's window and nothing of the raster outside it: the sync, the blanking and whatever a program draws past the window's edge go unseen.
- `screen` draws memory as it stands, in one mode and one palette. A picture a program makes by changing the mode, the inks or the screen's start partway down a frame, or by writing memory as the beam passes, is shown by `monitor` and not by `screen`, and `screen` reads the 6845's geometry as it stands at the moment it is asked, which a program that splits its frame changes within it.
- A base given to `screen` is an address, which cannot carry what bits 3 and 2 of the 6845's R12 say: that a row runs on past its 2K into the next 16K, as on a screen of 32K. A screen asked for no base reads them from the 6845; one given a base reads as though they were clear.
- Only a CPC's memory is read as a picture. A Spectrum's picture is shown by `monitor`, and its memory is not drawn otherwise.
- A picture is one picture. Nothing lays several side by side or labels them, marks the beam's progress across memory, or marks what was written lately; an agent asks for each picture and compares them itself, and no tool waits for the picture to change.
- `disassemble` reads bytes as instructions from wherever it is told and tells code from data no better than that: bytes after a jump or a restart that never returns there are read as instructions all the same. It follows no jumps and knows no names a program was written with.
- A request cannot be taken back. A client that stops waiting for a run leaves the machine to run the whole of what it asked, which the machine's tick in its next answer shows; the limit on a request keeps that to half a minute of the machine's time, or a minute of a CPC's whose frames do not come.
- `set` refuses only what the emulator could not run from, so a machine written through its machinery can stand where no silicon could, and run on from there.
- The machines live only as long as the server. When its input closes, they are put away with it, nothing of them is kept but the snapshots saved of them and the journals read of them, and the next server gives out the same handles again, and the same names to its states.
- One client speaks to one server, over its standard input and output and nothing else.
